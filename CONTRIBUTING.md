## What we accept

- Bug fixes with a regression test that fails before the fix and passes after.
- New webhook handlers or behaviour changes backed by an official RevenueCat docs citation. Link the doc in the PR.
- Additions to the client SDK surface with matching tests, TypeScript types, and README updates.
- Dependency updates that close a real CVE or unblock a feature. Include `npm audit --audit-level=high` output in the PR.
- Documentation fixes that correct inaccuracies. Verify against the code.

## What gets rejected

- PRs without tests. Every behaviour change lands with a test. Every new public method lands with a test.
- Speculative handling of undocumented RC wire values. If you cannot cite the official docs, a captured payload, or SDK source, we assume it does not ship. Examples of past speculative code that got removed: the `cancel_reason: "SUBSCRIPTION_PAUSED"` branch in `processCancellation`.
- Emojis in source, docs, comments, commits, CHANGELOG, or PR bodies.
- Breaking changes without a MINOR version bump (see `CHANGELOG.md` for the `0.1.x` to `0.2.0` pattern). Pre-1.0, anything observable to consumers is at least MINOR.
- `console.log` or commented-out code left in the diff.
- TODOs without a linked GitHub issue.
- Commit messages that do not follow the convention below.
- Any attribution to AI systems, AI-generated content notices, or co-authored-by trailers. Every commit and every piece of text has to read as if a human wrote it.
- Force-pushes to branches with review comments on them.

## Development setup

1. **Fork** the repository on GitHub.
2. **Clone** your fork:

   ```bash
   git clone https://github.com/<your-username>/convex-revenuecat.git
   cd convex-revenuecat
   ```

3. **Branch off `main`** with a descriptive name:

   ```bash
   git checkout -b fix/handlers-price-change-propagation
   ```

4. **Install**:

   ```bash
   npm install
   ```

5. **Verify the baseline passes** before you change anything:

   ```bash
   npm run validate
   ```

   If `validate` is red on `main`, open an issue before touching anything else.

6. **Start dev mode** while you work. This watches and rebuilds codegen + types:

   ```bash
   npm run dev
   ```

## Running the example app

The `example/` directory is a full Convex app that consumes the component. Use it to exercise changes end to end before you submit.

```bash
cd example
npm install
npx convex dev
```

This gives you a live Convex deployment with the component mounted. You can then POST real webhook payloads at the HTTP endpoint and watch state change. Sample payloads for every RC event type live under `src/component/handlers.test.ts` and `src/component/audit-fixes.test.ts`. Copy one into a `curl` call to test manually.

## Code style

- TypeScript `strict: true`. No implicit `any`. No `// @ts-ignore` without a comment explaining why and a linked issue.
- Every Convex function (query, mutation, action) requires `args` and `returns` validators. No exceptions.
- Webhook handler `args` use `v.any()` for the event payload, not `v.object`. RC reserves the right to add fields without versioning, and a strict validator drops real events. Cast to `EventPayload` inside the handler. See `src/component/handlers.ts` for the existing pattern.
- Query return validators use the schema pattern: `schema.tables.X.validator.extend({ _id: v.id("X"), _creationTime: v.number() })`. Do not re-declare field lists.
- `hasEntitlement` and `getActive` stay pure expiry: `isActive && (expiresAtMs === undefined || expiresAtMs > now)`. Grace periods are folded into `expiresAtMs` by `processBillingIssue` and `syncSubscriber`. Do not add short-circuits on `billingIssueDetectedAt`, `gracePeriodExpirationAtMs`, or any other auxiliary flag. This mirrors iOS `EntitlementInfo.isActive` and keeps access gating correct when an `EXPIRATION` event is dropped.
- Every new webhook handler begins with `await recordEvent(ctx, event)`. This upserts the customer and hydrates experiments. Do not call `upsertCustomer` or `upsertExperiments` directly.
- New state transitions flow through `snapshotEntitlements` + `fireTransitionHooks` in `webhooks.ts`. Do not schedule hooks yourself from inside a handler.
- Internal writes use `internalMutation`. Public queries use `query`. Public mutations are rare (`customers.purge` is the main one) and require review.
- Small functions. One concern per function. Early returns over nested conditionals.
- Default to writing zero comments. Only comment when the WHY is non-obvious. Never narrate what the code does when the identifiers already say it.
- Delete unused code. Do not leave dead exports, dead branches, or commented-out blocks.
- No emojis anywhere. Not in code, not in comments, not in user-facing strings, not in tests, not in commit messages, not in CHANGELOG, not in PR bodies.

## Testing requirements

Every behaviour change and every new feature lands with tests. Pure refactors don't have to add tests, but they can't remove coverage.

Run the full suite locally:

```bash
npm run test              # full suite via Vitest
npm run test -- handlers  # single module
npm run typecheck         # tsc --noEmit + example typecheck
npm run lint              # ESLint
npm run validate          # all three in one shot (also what CI runs)
```

`npm run validate` must be green before you open the PR. CI will re-run it.

### Unit tests

Unit tests live next to the module under test (`src/component/handlers.ts` is tested by `src/component/handlers.test.ts`). They use `convex-test` with `setup.test.ts` as the harness.

For every change, cover:

1. **Happy path**: the event or call produces the expected state mutation.
2. **Idempotency**: running it twice yields the same result (for dedup-relevant paths).
3. **Edge cases**: missing optional fields, unknown enum values (they should fall back, not throw), empty arrays, `null` vs absent keys.
4. **Error handling**: invalid auth, missing required fields, payload size overflows.

If you add a new webhook handler, cover:

- The event reaches the correct handler via the dispatch table in `webhooks.ts`.
- Multi-entitlement events (where applicable) produce one state mutation per entitlement.
- The `webhookEvents` audit table records the event.
- Dedup: replaying the same `event.id` is a no-op.

### End-to-end tests via the example app

The `example/convex/` directory includes its own test suite that exercises the component as a consumer would. If your change affects the client SDK, the HTTP handler, or the public query surface, add an integration test to `example/convex/example.test.ts` or create a new test file in that directory.

For webhook-processing changes, the integration test should:

1. Post a real captured payload to the HTTP handler (via `convex-test`'s HTTP simulation).
2. Assert the resulting state via the public query methods (`hasEntitlement`, `getActiveSubscriptions`, etc.).
3. Assert any side effects (`_scheduled_functions` rows for hooks, `webhookEvents` rows for the audit log).

For client SDK changes, add a test that instantiates the `RevenueCat` class with mock `components.revenuecat` and calls every affected method.

### Coverage expectations per change type

| Change | Unit tests | Integration test | Docs update |
| --- | --- | --- | --- |
| Bug fix in a handler | Regression test that fails before, passes after | Yes, if the bug was consumer-visible | `CHANGELOG.md` entry |
| New webhook handler | Happy path + dedup + multi-entitlement + audit log | Example app test firing the payload | README event table + `CHANGELOG.md` |
| New client SDK method | Invocation + return type + error paths | Example app consumer test | README API table + usage example + `CHANGELOG.md` |
| Schema field addition | Validator accepts new values + migration compatibility | Yes, if the field is exposed via queries | README if publicly visible + `CHANGELOG.md` |
| Lifecycle hook change | Scheduling assertion via `_scheduled_functions` + dedup + no-hook overhead check | Yes | README lifecycle section + `CHANGELOG.md` |
| Sync / REST change | Mock subscriber response + assert reconciliation | Yes, via `syncSubscriber` in the example | README sync section + `CHANGELOG.md` |

## PR type playbooks

Different kinds of change have different gotchas. Find the section that matches yours.

### Webhook handler PRs

1. Link the RevenueCat docs page that describes the event or field you are handling. If the docs don't cover it, open an issue first so we can discuss whether it should be handled at all.
2. Capture a real payload. Either paste it from your own deployment's `webhookEvents` table (redact PII) or use the sample events page. Add it as a test fixture.
3. Add a test that posts the payload and asserts the resulting database state.
4. Add a dedup test (same `event.id`, different `event_timestamp_ms`, assert the handler ran once).
5. If the event affects entitlement state, add a lifecycle hook test asserting the correct hook fires with the documented args.
6. If the event affects multiple entitlements, assert one handler invocation per entitlement.

### Lifecycle hook PRs

1. Lifecycle hooks live in `src/component/transitions.ts`. The firing path is in `src/component/webhooks.ts` (snapshot before handler, handler runs, snapshot after, diff, fire).
2. New transition types require assertions on `_scheduled_functions` via `ctx.db.system.query("_scheduled_functions").collect()`. See `hooks.test.ts` for the pattern.
3. New hook args require updates to the `LifecycleHooks` type in `transitions.ts`, the client-side `RevenueCatOptions.hooks` type in `client/index.ts`, and the README lifecycle section.
4. Any new hook must have a "no hooks configured = zero scheduled jobs" test that proves consumers without hooks pay zero overhead.

### Schema PRs

1. New fields on existing tables must be `v.optional()`. Required fields break existing data and will not merge.
2. New indexes require a sentence in the PR explaining which query reads them. Unused indexes cost write amplification.
3. New validators (enums) go in `src/component/schema.ts` as named exports. Reference them from handler args and query returns.
4. If the field is exposed via a public query, update the README and `CHANGELOG.md`.

### Client SDK PRs

1. New methods go on the `RevenueCat` class in `src/client/index.ts`.
2. The matching internal surface goes on `ClientComponentApi` in the same file. Use `FunctionReference` with the proper visibility (`AnyVisibility`).
3. Return types must be concrete. No `any`, no `unknown` without justification. Tighten generics where possible.
4. Add a test that mocks `components.revenuecat` and asserts the method calls the right underlying mutation/query with the right args.
5. Update the README API table and add a usage example under `## Usage`.

### Sync / REST PRs

1. If you change how we read RC's REST response, capture a real `/v1/subscribers/{id}` response and add it as a fixture in `sync.test.ts`.
2. All new fields read from the REST response need to be propagated through `upsertSubscription` and mapped to the component's internal shape.
3. Cross-check against the webhook handler path: any field that can come in via webhook should also come in via sync, and vice versa.

### Documentation PRs

1. Verify every code snippet actually runs. Stale snippets (like the pre-0.2.0 `convexTest()` testing example) are a real hazard and get copy-pasted into production.
2. Cross-check claims against the code. If the README says "redactor strips X", open `src/client/index.ts` and confirm.
3. Respect the voice in `~/.claude/rules/voice.md` (or ask me if unsure): no em-dashes, no banned words list, no bold-prefixed bullets, no emojis.
4. No API drift. If you add a method or change a signature, the README API table, the CHANGELOG, and the example app must all move together.

## Commit convention

One logical change per commit. Each commit message follows:

```
type(scope): lowercase description under 72 chars, no trailing period
```

**Types**: `feat`, `fix`, `docs`, `refactor`, `perf`, `chore`, `test`, `ci`, `build`.

**Preferred verbs**: add, fix, extract, drop, rename, move, split, wire, swap. Avoid `implement`, `utilize`, `leverage`, `enhance`, `streamline`.

**Scope** is the module or area: `handlers`, `sync`, `webhooks`, `schema`, `client`, `hooks`, `docs`, `readme`, `changelog`, `example`, `test`, `deps`, `build`, `audit`.

**Examples that merge**:

```
fix(handlers): revoke on cancellation when price is negative
feat(hooks): add onCustomerDeleted wired to customers.purge
docs(readme): correct webhook retry policy timing
refactor(sync): extract period_type mapping to shared helper
test(handlers): cover multi-entitlement expiration dedup
```

**Examples that get rejected**:

```
Update handlers.ts                    (no type, no scope, vague)
feat: add feature                     (what feature?)
fix(handlers): Implement refund logic.  (trailing period, banned verb)
feat(hooks): add hooks + fix sync bug  (two concerns in one commit)
```

Never use `Co-authored-by:` trailers, never reference AI systems, never say "generated by". Commits must read as human-written.

## Before submitting

Run through this list. If any item is not true, fix it before opening the PR.

- [ ] `npm run validate` is green (test + lint + typecheck).
- [ ] `npm audit --audit-level=high` reports 0 vulnerabilities.
- [ ] Test coverage added for every behaviour change (see the coverage table above).
- [ ] Integration test added in `example/convex/` if the public surface changed.
- [ ] `CHANGELOG.md` updated under `## [Unreleased]` with a dated-when-released entry. Reference files and symbols in backticks.
- [ ] `README.md` updated if the public API, webhook handling, hook args, or configuration options changed.
- [ ] Version implications considered: does this require a MINOR bump? Pre-1.0, behavior changes are MINOR.
- [ ] No `console.log`, no commented-out code, no unused imports, no unused exports.
- [ ] No TODO without a linked GitHub issue (URL or `#123`).
- [ ] No emojis in any file you touched.
- [ ] Commits follow the convention above. One concern per commit.
- [ ] PR body starts with a verb describing what changed and why.
- [ ] PR body cites the RevenueCat docs page or SDK source for any webhook or enum changes.

## PR description template

Use this as a starting point. Delete sections that don't apply. Do not add sections for "Impact: none" or "Migrations: none" if they don't apply.

```markdown
<one-line summary starting with a verb, no preamble, no headers at top>

<one-to-three sentences: what changed and why, the problem it solves,
any consumer-observable behavior change>

<optional: link to the RC docs page or SDK source that supports this change>

Changes:
- `src/component/handlers.ts`: <what was done>
- `src/component/handlers.test.ts`: <coverage added>
- `README.md`: <doc updates>
- `CHANGELOG.md`: <entry added>

Test plan:
- `npm run validate` passes locally
- New regression test at `src/component/handlers.test.ts:<line>` fails on main, passes on this branch
- Integration test at `example/convex/example.test.ts:<line>` covers the consumer path
- Manual: posted captured payload to `http://localhost:3210/webhooks/revenuecat`, verified entitlement revokes via `hasEntitlement` query

Breaking change: <only include if there is one, describe consumer impact>
```

Keep it short. Reviewers read the diff, not a novel. But the test plan is non-negotiable: list exactly how you verified the change works.

## Security

Report vulnerabilities by email rather than a public issue. The component handles webhook auth secrets and mirrors payment state, so a responsible disclosure window matters. A written `SECURITY.md` is coming; until then, reach me through the contact on the GitHub profile.

Do not open a public PR that references an active vulnerability. Open the PR against a private fork, then loop me in.
